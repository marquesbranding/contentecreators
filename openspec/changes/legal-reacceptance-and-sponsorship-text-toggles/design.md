## Context

- `legal_documents` guarda versões (`document_type`, `version_label`, `content_hash`, `active_from`, `retired_at`). `TERMS 1.0` e `PRIVACY 1.0` (PDFs em `public/legal/`, metadados em `src/features/legal/content/legal-pdfs.ts`) já estão inseridos pelas migrations `20261013120000`, `20261013140000`, `20261013150000`; placeholders foram aposentados. `account_consents` tem índice único `(account_id, legal_document_id)`. A migration `20261013140000` registra que nenhum consentimento referencia a `1.0` ainda → todo usuário existente está pendente.
- Hoje o aceite só acontece em `src/features/onboarding/server/repositories/drizzle-onboarding-registration.repository.ts` (~linha 650-700) ao enviar o cadastro.
- RLS: `account_consents_insert_policy` só permite INSERT para `INFLUENCER`/`COMPANY` em `ONBOARDING|CHANGES_REQUESTED|APPROVED` (`app_can_edit_own_profile()`); `PENDING_REVIEW` ficaria de fora. Por isso o aceite usa função `SECURITY DEFINER` (mesmo padrão de `app_confirm_whatsapp_contact`).
- Precedente de UI: `src/features/whatsapp-contacts/` (modal montado em `src/app/(product)/app/layout.tsx`, query server-side + `VerifiedAccountTransactionError` `UNAUTHENTICATED` → lista vazia). Copiar essa estrutura.
- Patrocínios: opções criativas vivem como colunas em `sponsorship_placements` (migration `20260918120000_sponsorship_creative_options.sql`), espelhadas em `src/db/schema/sponsorships.ts` e propagadas por `types`, `schemas`, repositórios, serviços e componentes (ver tasks). A entrega pública é montada em `src/features/sponsorships/server/services/sponsorship-delivery.service.ts` (admin-authored ~l.163-181; participant-derived ~l.99-124).

## Goals / Non-Goals

**Goals:**
- Re-aceite derivado do estado do banco (sem lista manual de usuários): publicar nova versão ativa ⇒ modal reaparece.
- Fluxo sem erro: abrir PDF, baixar PDF, checkbox, salvar, fechar.
- `show_title` / `show_body` decididos por checkbox; título/texto continuam salvos e visíveis na listagem.
- Servidor nunca entrega ao público texto marcado como oculto.

**Non-Goals:**
- Bloquear Server Actions/APIs até o aceite (o modal é um gate de UX; ver Riscos).
- Mostrar o modal para `ADMIN`, `ONBOARDING` ou `SUSPENDED`.
- Aceite de `CONTACT_VISIBILITY` (continua no perfil do criador).
- Alterar `FEATURED_CREATOR` (conteúdo vem do perfil do criador).
- Mexer em migrations já aplicadas.

## Decisions

1. **Pendência derivada, não flag por usuário.** Pendente = documento ativo mais recente de `TERMS`/`PRIVACY` sem `account_consents`. Alternativa descartada: coluna `needs_reacceptance` em `accounts` — exigiria UPDATE em massa e lembrar de repetir a cada versão. A "migration que deixa pendente" é: (a) as funções abaixo, (b) um `DO $$` que valida que `TERMS 1.0`/`PRIVACY 1.0` existem e ativos e faz `RAISE NOTICE` com a contagem de contas que ficarão pendentes. Nenhum consentimento histórico é apagado (evidência legal).
2. **Duas funções SQL `SECURITY DEFINER`, `SET search_path TO ''`, `REVOKE ALL FROM PUBLIC; GRANT EXECUTE TO contente_app_user`:**
   - `public.app_list_pending_legal_documents()` → `TABLE(id uuid, document_type public.legal_document_type, version_label varchar, published_at timestamptz)`. Usa `app_context_is_verified()`, `app_current_account_id()`, `app_current_role()`, `app_current_status()`; retorna zero linhas fora do escopo (role ≠ INFLUENCER/COMPANY ou status ∉ PENDING_REVIEW/CHANGES_REQUESTED/APPROVED). `SELECT DISTINCT ON (document_type) … ORDER BY document_type, active_from DESC, published_at DESC` filtrando `retired_at IS NULL AND active_from <= now()`, depois `NOT EXISTS` consent.
   - `public.app_accept_legal_documents(document_ids uuid[], request_id text)` → `integer` (linhas inseridas). Recalcula o conjunto pendente; se `document_ids` não for exatamente esse conjunto (comparar como arrays ordenados) levanta `errcode '22023', message 'legal_documents_not_current'`; se o conjunto pendente for vazio retorna 0 (idempotente). Insere com `context = jsonb_build_object('flow','reacceptance','legalCopyApproved',true)` e `ON CONFLICT (account_id, legal_document_id) DO NOTHING`. O trigger `capture_audit_revision` já audita `account_consents`; o contexto de auditoria vem de `applyVerifiedAuditContext`.
   Alternativa descartada: usar o INSERT direto com RLS — falha para `PENDING_REVIEW`.
3. **Nova feature `src/features/legal-acceptance/`** espelhando `whatsapp-contacts` (`index.ts`, `server.ts` com `import "server-only"`, `components/`, `server/{actions,queries,repositories}/`, `types/`). Ela importa de `@/features/legal` e de `@/features/identity/server`. Antes de criar imports cruzados, conferir as regras do `eslint-plugin-boundaries` (`npm run lint`) e `docs/architecture/slices.md`.
4. **PDFs por versão.** Adicionar em `src/features/legal/content/legal-pdfs.ts` a lista `publishedLegalPdfs` e em `src/features/legal/domain/` uma função pura `findLegalPdf(documentType, versionLabel): LegalPdfDocument | null`; exportar por `src/features/legal/index.ts`. O DTO do modal junta a linha do banco com esse registro (`pdfUrl`, `downloadName`, `title`, `updatedLabel`). Sem registro ⇒ item aparece sem links (e o servidor loga `operationalLogger.warn`), mas o aceite continua possível. Versão futura = novo arquivo `…v1.1.pdf` + entrada no registro + migration (regra já documentada no arquivo).
5. **Modal.** Client component com o `Dialog` de `@/shared/components/ui/dialog` aberto (`open`), `showCloseButton={false}`, e `onOpenChange` ignorando fechamentos (bloqueia Esc/overlay). Estado local: `accepted` (checkbox), `isPending` (`useTransition`), `errorMessage`. Abrir = `<a href={pdfUrl} target="_blank" rel="noopener noreferrer">`; baixar = `<a href={pdfUrl} download={downloadName}>`. Checkbox `@/shared/components/ui/checkbox` com `<label>`. Botão primário `disabled={!accepted || isPending}` com `Spinner`. "Sair" usa `signOutAction` de `@/features/identity/server` em um `<form action>` (ver `sign-out-button.client.tsx`). Sucesso: `router.refresh()` e fecha (estado local `resolved`). Erro `legal_documents_not_current`: mensagem "Os documentos foram atualizados. Recarregamos a página." + `router.refresh()`. Qualquer outro erro: `Alert`/`toast.error` e mantém o modal.
6. **Server Action** `acceptLegalDocumentsAction({ documentIds })`: valida com Zod (`z.array(z.uuid()).min(1).max(5)`), `runVerifiedAccountTransaction({ preferredRole: "NON_ADMIN", requestId })`, chama `applyVerifiedAuditContext` (reason "Re-accepted updated legal documents", `source: "APPLICATION"`), `select public.app_accept_legal_documents(...)`. Retorna `{ kind: "accepted" } | { kind: "stale" } | { kind: "error" }`. Não usa `revalidatePath` (o cliente faz `router.refresh()`).
7. **Montagem.** `loadPendingLegalDocuments()` roda em `Promise.all` no layout `/app` e em `onboarding/layout.tsx`, tratando `VerifiedAccountTransactionError` `UNAUTHENTICATED` e conta ausente como `[]` (igual ao precedente do WhatsApp). Telas de login/cadastro/role selection não montam o modal. O modal de WhatsApp e o de aceite podem coexistir: renderizar o de aceite **depois** e, no componente do WhatsApp, nada muda (Radix/Base UI empilha; o de aceite é o último e fica por cima).
8. **Onboarding tolerante.** No insert de `account_consents` do onboarding (e em qualquer outro insert de consentimento de TERMS/PRIVACY, ex.: `drizzle-corrected-profile-resubmission.repository.ts` — verificar), usar `.onConflictDoNothing({ target: [accountConsents.accountId, accountConsents.legalDocumentId] })`.
9. **Patrocínio: colunas e invariantes no banco.** Migration `20261014190000_sponsorship_text_visibility.sql`: `ADD COLUMN show_title boolean NOT NULL DEFAULT false, ADD COLUMN show_body boolean NOT NULL DEFAULT false`; constraints `sponsorship_placements_show_title_check CHECK (NOT show_title OR title IS NOT NULL)` e `sponsorship_placements_show_body_check CHECK (NOT show_body OR body IS NOT NULL)`. **Ordem:** adicionar colunas → backfill → adicionar constraints. Backfill desabilita/reabilita `sponsorship_placements_updated_at_version_trigger` exatamente como a migration `20260918120000` (preserva `version`/`updated_at`; auditoria continua ligada): `UPDATE … SET show_title = (title IS NOT NULL), show_body = (body IS NOT NULL)`. Para `FEATURED_CREATOR` isso é inofensivo (title/body normalmente nulos).
10. **Filtro na entrega, no servidor.** No ramo admin-authored de `sponsorship-delivery.service.ts` (e no equivalente do repositório `drizzle-sponsorship-delivery.repository.ts`, que seleciona colunas), mapear `title: placement.showTitle ? placement.title : null` e `body: placement.showBody ? placement.body : null`. O DTO público (`RendererPlacementDto`) **não** ganha as flags (menos superfície; `allowedPromotionKeys` em `public-sponsorship-promotion.api.ts` fica igual). Os componentes (`sponsorship-hero-banner.tsx`, `sponsorship-catalog-card.tsx`, carrossel, side placement) já omitem título/texto quando `null`, então não mudam. O ramo participant-derived (`FEATURED_CREATOR`) recebe o mesmo filtro (decisão revisada na apply: a regra do pedido vale para todo patrocínio). Alternativa descartada: filtrar só no componente (vazaria o texto oculto no JSON/HTML).
11. **Backoffice DTO/formulário.** `showTitle`/`showBody` entram em: `SponsorshipPlacementDraft` e `PlacementCreative`-adjacentes de gestão (`types/sponsorship-placement.types.ts`), `sponsorshipPlacementDraftBaseSchema` (Zod `z.boolean().default(false)`) + novo refinamento em `addCreativeLinkIssues` (mensagens "Informe o título para exibi-lo." / "Informe o texto para exibi-lo.", paths `showTitle`/`showBody`), `placement-form.schema.ts` (tipo, defaults, `showTitle: placement?.showTitle ?? false`), `placement-form-dialog.client.tsx` (payload), `sponsorship-management-view.service.ts` (DTO de gestão e mapeamento de entrada), `admin-sponsorship-placement.service.ts` (evidência/auditoria e cópia), `sponsorship-placement.repository.ts` + `drizzle-sponsorship-placement.repository.ts` (colunas), `sponsorship-placement-policy.ts` (`activationPayload`), e `placement-content-step.client.tsx` (UI). UI: reutilizar `PlacementCheckbox` (ampliar o tipo `name` para incluir `showTitle` | `showBody`) abaixo dos campos `title` e `body`; `disabled` quando `values.title.trim() === ""` (idem body); um `useEffect` com `useWatch` desmarca a flag (`form.setValue(..., false)`) quando o campo fica vazio. `PlacementCheckbox` precisa aceitar prop `disabled`.
12. **Prévia e listagem.** `placement-live-preview.client.tsx` (~l.82-98): `title: values.showTitle && values.title ? values.title : null`, idem body. Em `sponsorship-management-view.client.tsx` (l.214, 525, 607-616) continuar mostrando o texto salvo e acrescentar um `Badge` discreto "Título oculto na arte" / "Texto oculto na arte" quando a flag é falsa e o conteúdo existe.
13. **Dados locais.** `supabase/seed.sql` (inserts de `sponsorship_placements`, ~l.524 e ~l.583): incluir `show_title`/`show_body` verdadeiros onde há título/texto, para as telas locais continuarem como estão.

## Risks / Trade-offs

- [Gate só de UX: um usuário pendente ainda poderia chamar APIs diretamente] → Aceito nesta entrega (o objetivo é coletar o aceite no login). Se for necessário bloqueio duro, abrir mudança separada com guard em `account-access.guards.ts`.
- [PDF sem entrada no registro] → modal ainda permite aceitar; log de warn; teste unitário garante que `1.0` TERMS/PRIVACY estão registrados.
- [Corrida: nova versão publicada com modal aberto] → função rejeita ids defasados (`legal_documents_not_current`); UI recarrega.
- [Backfill muda aparência] → backfill preserva exatamente o que era exibido (flag = conteúdo existente).
- [Constraint nova falha em prod por dado inconsistente] → impossível: backfill roda antes das constraints e `show_* = (campo IS NOT NULL)`.
- [Dois modais empilhados (WhatsApp + aceite)] → aceite renderizado por último; teste de componente não precisa cobrir, mas verificar visualmente no e2e.
- [Prints dependem do stack local] → tasks exigem `npm run local:reset` e `npm run test:integration:local`.

## Migration Plan

1. Aplicar localmente: `npm run local:reset` (ou `npm run db:migrate`). Conferir `NOTICE` com contagem de contas pendentes.
2. `npm run test:integration:local` verde (inclui drift Drizzle × SQL em `src/db/core-schema.integration.test.ts`).
3. Deploy: migrations primeiro (compatíveis com o código antigo: colunas com default, funções novas), depois a aplicação. Rollback: voltar a release; correção de banco só com nova migration.
4. Produção: `NOTICE` da migration informa quantos usuários verão o modal no próximo login.
